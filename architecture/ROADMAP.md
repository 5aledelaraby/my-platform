# خريطة التوسع: كل مجال له مكان جاهز، لكن مفيش حاجة تتبني قبل ما تُطلب

الفكرة: **مش بنبني وحدات فاضية من دلوقتي.** بنحدد لكل مجال مستقبلي: أين يعيش، ومتى يستحق الإنشاء، وعلى إيه يعتمد. وبعدين الإضافة نفسها تاخد دقيقتين بأمر واحد:

```bash
node tools/architecture/new-unit.mjs package <name> [--may-import a,b]
node tools/architecture/new-unit.mjs app <name> [--may-import a,b]
```

الأمر بيعمل الهيكل (package.json وtsconfig وsrc) ويسجل الوحدة في `architecture/boundaries.json`، وبيشغّل فحص الحدود. القواعد بعد كده تتفرض تلقائيًا في الـ CI.

## ثلاث أسئلة قبل إنشاء أي وحدة جديدة

1. **في مستهلك حقيقي دلوقتي؟** (تطبيق أو وحدة تانية محتاجاها فعلًا). لو لأ، خلّي الكود جوه الوحدة اللي بتستخدمه.
2. **ليها حدود واضحة؟** تقدر تكتب سطر واحد بيقول إيه اللي تملكه وإيه اللي ما تعرفوش.
3. **اتجاه الاعتماد معروف؟** مين يستورد مين، بدون دورات.

## الموجود فعلًا

| المجال | المكان | الحالة |
|---|---|---|
| منتجات، سلة، أسعار، خصم، شحن | `packages/commerce` | جاهز ومختبر |
| SEO (canonical، robots، sitemap، JSON-LD) | `packages/seo` | جاهز ومختبر |
| محتوى ومقالات | `packages/content` | نموذج التحقق جاهز |
| مكونات التصميم | `packages/ui` | هيكل فاضي |
| الواجهة الأمامية | `apps/website` | محتاج scaffold لـ Astro |
| إنشاء الطلبات وتخزينها (D1) | `apps/api` | جاهز ومختبر، محتاج نشر على Cloudflare (ADR 0008) |

## المجالات المستقبلية

| المجال | أين يعيش | يتبني لما... | يعتمد على |
|---|---|---|---|
| لوحة الإدارة | `apps/admin` | تعدّل المنتجات والمحتوى من واجهة بدل ملفات | api + `packages/auth` |
| المخزون | جزء من `commerce` أولًا، ويتفصل لو كبر | تتابع كميات فعلية | commerce |
| الدفع الأونلاين | `packages/payments` | تختار مزود دفع | commerce (وapi يستدعيه) |
| الإيميل والإشعارات | `packages/notifications` | تبعت تأكيدات أو نشرات | لا شيء داخلي |
| التتبع والإعلانات (Pixel وCAPI) | `packages/tracking` + `apps/capi-worker` | تنقل الـ CAPI من الموقع القديم | لا شيء داخلي |
| الخدمات (مثل التفصيل بجلد طبيعي) | صفحات في `content/` أولًا، وحزمة `services` لو احتجت حجز وقت أو تسعير خاص | الخدمة ليها منطق (حجز، عروض أسعار) | content, commerce |
| السفر | تطبيق منفصل `apps/travel` (أو براند آخر) يعيد استخدام `ui`/`seo`/`content` | يبقى له كتالوج ونموذج بيانات خاص | ui, seo, content |
| الميديا والصور | `packages/media` + تخزين R2 | ترفع صور من لوحة الإدارة | لا شيء داخلي |
| النشر على السوشيال | `apps/social-worker` + `packages/social` | توصل أول منصة فعلًا | content, media |
| تكامل مع خدمة خارجية | `packages/integration-<اسم الخدمة>` (واحدة لكل خدمة) | تحتاجها فعلًا | حسب الحاجة |
| تعدد اللغات | داخل `content` و`apps/website` (routing)، مش حزمة جديدة | تضيف لغة تانية | content |
| المصادقة | `packages/auth` | تظهر لوحة الإدارة | لا شيء داخلي |

## هيكل الموقع (ADR 0009)

الرئيسية `/` تعريف بالبراند فقط، والمتجر تحت `/belts/`. كل مجال جديد (خدمات، سفر، مقالات...) ياخد قسم رئيسي خاص بيه، والرئيسية بتربط عليه لما يتطلق بدون ما تعرض محتواه.

## قواعد ثابتة مهما كبرنا

- الوحدات النقية (commerce, seo, content, payments...) **ممنوع** تستورد React أو Astro أو أي framework.
- التطبيقات (`apps/*`) هي الوحيدة اللي تجمع الحزم مع بعض. حزمة ما تستوردش تطبيق، وتطبيق ما يستوردش تطبيق.
- كل تكامل خارجي معزول في حزمته. مفاتيحه تيجي من التطبيق (Cloudflare Secrets)، **ممنوع** داخل الحزمة.
- أي اتجاه اعتماد جديد = سطر في `boundaries.json` + ADR قصير.
- لو وحدة اتجمدت من غير مستهلك بعد فترة طويلة، تتحذف. الكود الميت أغلى من إعادة إنشائه.
